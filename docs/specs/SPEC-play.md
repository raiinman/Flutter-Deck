## Source of truth
The game side's `LAUNCHER-CONTRACT.md`, version 2.0, sections 9 to 12 (and, for the sharper picture, version 2.4, section 16) (kept with the recompilation work, local only, not in this repository). This document says how Flutter Deck follows it. The earlier 1.x program is recognised by its hash and refused with advice to choose the newer one.

## Never bundled
The game program (`rock_neo_rt_hp.exe`, `rock_neo_rt_hd.exe` or `rock_neo_rt_fd.exe`) contains translated game code. Flutter Deck never contains, downloads, copies or releases it, the disc image, anything read from the disc, or a memory card. It stores where the user's own game program is. `check-runtime.ps1` fails if any packaging script, the installer or the updater names them.

## What the user sets (setup and readiness screen, game 1)
The game settings appear there only when Mega Man Legends 1 is the selected game and the saved settings could be read. Before that the cog opened the feature list. Observed in a scratch copy through UI Automation: both new routes open the screen. The button on the Settings screen was not tried by a person. Since 2026-11-18 the Library has three more Play controls (card, menu, panel; SPEC-library.md, "Play from the Library"). They press this same Play button through `PressPlay` in `DeckLibrary.cs`, only while it is enabled, so the readiness rules here are unchanged. The round Play button itself is no longer shown. Since the Library became an icon grid (2026-11-17, SPEC-library.md) the cog is on the game's page: click the Mega Man Legends icon first. The Settings, Home and Help buttons are unchanged.
- Game program: the user's `rock_neo_rt_hc.exe` (contract 2.6, recommended: also reads Xbox pads in all four slots and PlayStation 5 pads over USB or Bluetooth, nothing for the launcher to set), `rock_neo_rt_hp.exe` (contract 2.5: sharper smooth picture and window height presets), `rock_neo_rt_hd.exe` (2.4) or `rock_neo_rt_fd.exe` (2.0, original picture only). A full path is required; a relative one in a hand-edited settings file is refused.
- Disc image: the `.cue` already chosen in Setup. The game reads its own program (`ROCK_NEO.EXE`) straight from that disc image, so there is no separate disc-program setting any more. BIOS is not needed.
- Memory card: nothing to set. The first time Play is pressed the game creates an empty card in Flutter Deck's folder, and saving works from then on. To continue earlier progress instead, a card can be copied in before the first Play from a file the user picks (a raw 131,072-byte card, or a `.gme` save the game converts). The picked file is only read, and a card Flutter Deck already has is never replaced by this step. The one thing that replaces the card is Restore on the Saves screen (SPEC-saves.md).
- Game window size (480p, 720p, 1080p, 1440p, 4K for a program that reports `window-height`; otherwise 2x to 6x), game volume 0 to 100, and a sound-off checkbox. Other stored values fall back to 720p (or 3x) and 100.
- Stored in `runtime.xml` in the launcher's settings folder. The card, key map, session files and start-failure file live in `games\mml1\` under that folder.

## When Play is on
Only for game 1, when the game program and disc image pass their checks, any existing card is the right size, the build is accepted (below), and no game is using the card. That is decided in one place (`UpdatePlay`), and everything is checked again, with a fresh hash, at the moment of starting.

## Build identity
1. The program file's SHA-256 is computed at every start. The three builds named in contracts 2.0, 2.4 and 2.5 are accepted. Any other build is blocked until the user presses "Use this game program build" and confirms; that acknowledges exactly that hash, and a changed file asks again. Choosing a different program clears the acknowledgement.
2. Only after that, the program itself is asked what it is (`--identity`, which prints a few lines and exits). It must report contract 2.x and the options Flutter Deck passes (`card-new`, `exe-from-disc`, `fail-file`, `volume`); otherwise Play stays off with the reason. An unaccepted program is never run, not even for this question. The answer is shown beside the game program on the setup screen. The program gets five seconds to answer and one more for its output to arrive. A good answer is remembered for that exact file content; a missing or bad answer is remembered for 30 seconds for that file location only, so the screen does not run a slow or broken program on every redraw, and it is asked again as soon as the user chooses a program or presses Play.

## The sharper picture (contract 2.4, `rock_neo_rt_hd.exe`)
- With the 2.4 build, the game itself decides the first time it is started as a play session: it shows a Yes/No window that tells the player the game now starts with a sharper smooth picture, and keeps the answer in its own small file (`%LOCALAPPDATA%\RockManX64\picture-choice.txt`). Flutter Deck passes no option for this, so a player who has not ticked "Play the original picture" sees that window once. (If the box is ticked before the first Play, `--original-picture` is passed, the game does not ask and stores no answer; the question appears at the first start after the box is unticked.) The window appears on top of Flutter Deck and the game; it is not Flutter Deck's.
- Flutter Deck adds one setting, "Play the original picture (turn the sharper picture off)", stored as `originalPicture` in `runtime.xml`. It is shown only when the game program reports the feature `first-boot-picture` in its `--identity` answer. When it is ticked, Flutter Deck passes `--original-picture`, which wins over the player's stored answer. The option is never passed to a program without that feature (the 2.0 build refuses unknown options).
- With the sharper picture the game's window starts at 960 x 720 (3 times), or smaller on a screen whose work area is smaller (contract 2.2: it never starts larger than the work area). "Game window size" 2x to 5x therefore gives that size, and 6x gives 1920 x 1440 (limited to the screen's work area). This is the game's window rule (contract 2.2); Flutter Deck passes `--scale` as before.
- Flutter Deck does not start the game with the sharper picture on its own by passing `--internal-scale`: the game's first-start window is how the player is told.

## Window size presets (contract 2.5, `rock_neo_rt_hp.exe`)
- HDR is not offered: the game's colours are ordinary (SDR).
- When the game program reports the feature `window-height` in its `--identity` answer, the "Game window size" list shows 480p (640 x 480), 720p (960 x 720, the default), 1080p (1440 x 1080), 1440p (1920 x 1440) and 4K (2160p, 2880 x 2160), and Play passes `--window-height H` instead of `--scale N`. The choice is stored as `windowHeight` in `runtime.xml` (only these five values are accepted; anything else falls back to 720).
- With the sharper picture the game draws internally at 3x (480p and 720p), 5x (1080p), 6x (1440p) or 9x (4K) to match, and fits the picture to the window. With the original picture it uses the largest whole multiple that fits (for 1080p that is 4x, 1280 x 960). A window larger than the screen's usable area (screen height minus the taskbar and the window frame) is shrunk to fit with the same shape; on a 1080p screen only full screen (F11 in the game) can show a true 1080p picture. 4K is the heaviest choice for the graphics card.
- A game program without that feature keeps the old list of 2x to 6x and `--scale N`.

## What Play runs
`<game program> --live --exe-from-disc ROCK_NEO.EXE --run-dir <data>\sessions --cue <disc image> --card0 <data>\card1.mcd (--card-new | --card-from-gme <data>\card-import.gme) --keys <data>\keys.ini --scale N --volume V [--mute] --fail-file <data>\start-failure.txt`
- With the feature `window-height`, `--window-height H` takes the place of `--scale N` (same position in the line).
- `--original-picture` is added at the end only when the setting above is ticked and the game program reports `first-boot-picture`.
- `--card-new` is passed on every start; per the contract it never touches a card that exists. While a copied-in `.gme` waits and no card exists yet, `--card-from-gme` is passed instead (the two may not be combined).
- Started directly, never through a shell, with no console window. Standard error is read until it closes and a bounded part is kept; the game always writes a report there, so only the exit code decides success.
- The session folder is created first, the key map is written if missing, and an earlier start-failure file is deleted (the game only writes it on exit 2 and never clears it).
- The key map file is written with the contract's fourteen default lines only if it does not exist or holds nothing (empty, or only blanks, line ends or a byte-order mark, up to 64 KB: such a map would mean no keys at all); a map with content is never rewritten.
- No test or diagnosis option is ever passed. Full screen, the settings file, a second card, sound recording and session naming are not used; full screen is not verified on the game side.
- One game per memory card. While a game runs, a small marker file beside the card (`session.lock`) names its process id, start time and program name. Any Flutter Deck (this one reopened, or a second one) then refuses to start another game on that card, whichever copy of the game program is chosen, and keeps Play and the file choosers off. Starting is serialised per card by a system mutex around "check the card is free, mark it, start", so two launchers pressing Play at the same moment cannot both pass. The card is marked before the game is started (first naming the launcher, then the game); if it cannot be marked, nothing is started. A marker whose process has ended, or whose process id now belongs to a different program, is ignored; stale markers are removed when Flutter Deck starts and when a game it started ends, using the same mutex. Not covered: a game started outside Flutter Deck on the same card file is not detected at all; if someone deletes `session.lock` by hand while a game runs, a different copy of the program could then be started on the same card (the identical program file is still refused); and if the game's own mark cannot be written after it starts, the card stays marked only while that launcher is open.

## When the game ends
- Exit 0: nothing is shown.
- Exit 2: "refused to start", with the reason the game wrote to the start-failure file (only one written since this start is used; standard error is the fallback) and the arguments used. Treated as a launcher problem.
- Exit 3: the `TRAP:` line found by searching the whole newest session log written since this session started (or, when there is no such log, the `TRAP:` line the game wrote to standard error), and the log's location. An earlier session's log is never used. This also covers a card that could not be created or a program not found on the disc.
- Any other code: the `RUN END:` line if there is one, and the log's location.
- A failed save leaves `card1.mcd.tmp` or `card1.mcd.unsaved-N.mcd`; Flutter Deck lists them on the setup and readiness screen and never deletes them.
- "Ask the game to close" sends the game window a close request (the contract's way to quit). There is no forced end and no hang detection yet: a hung game has to be ended by the user, after which the card is free again.
- While a game runs, the window size, volume, sound-off, Open Setup and build-confirmation controls stay usable; they only affect the next start.
- If the game program file changes while Flutter Deck is open, Play may still look ready; pressing it then refuses, and the setup screen asks for the new build to be confirmed.

## State and privacy
The state snapshot carries `play=` unavailable, needs-setup, ready, running or failed. Exit reasons, file locations and the build fingerprint are shown on screen only; they never go into the snapshot or the session log (which records only game-started, game-ended, game-ended-with-error).

## Uninstall
Removing settings at uninstall removes `runtime.xml` but never the memory card, key map or session files.

## Structure and command
`GameRuntime.cs` (no UI; every folder is a parameter), `GameRuntimePureTest.cs` (uses itself as a stand-in program that answers `--identity` like a contract 2.0 build), the Play wiring in `Program.cs`. Check: `powershell -NoProfile -File .\check-runtime.ps1`

## Controller vibration (contract 2.9, `rock_neo_rt_mr.exe`)

The original game has no vibration; the game program makes its own when the player loses life. For a program that reports the feature `rumble` the Play page has a check box "Controller vibration" (default on). Off: `--no-rumble`. Stored as `noRumble` in `runtime.xml`. Not tried on a real PlayStation 5 pad.

For a program that reports the feature `intro-movie` the Play page has a check box "Play the opening movie (the Capcom logo) before the game" (default on). Off: `--no-intro-movie`. Stored as `noIntroMovie` in `runtime.xml`. The movie is skippable with Esc, Enter or Space; nobody has watched it in a real play session yet.
