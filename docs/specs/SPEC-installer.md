# Installer and application identity

Status, 2026-11-16: built, tested on scratch folders, and run for real once on the developer's PC (one install and one uninstall, with the developer's go-ahead). It has not been run on any other PC, and nothing is published.

## Developer decisions (2026-11-16)
- Installer: built in this project with the same compiler as the launcher, no extra tools.

## Application identity
- `assets\FlutterDeck.ico` is the icon file the developer supplied on 2026-11-16: the ship on its own, in sizes 256, 128, 64, 48, 32, 24 and 16 px. See `assets\ICON-PROVENANCE.md`. (An icon generated earlier that day by cropping `ship.png` was replaced by it and never committed.)
- `build.ps1` embeds the icon in `FlutterDeck.exe`. Windows uses it for the file, shortcuts, the taskbar and the window.
- `AppInfo.cs` gives the file its details: product Flutter Deck, company Dead Signal Interactive, and a version taken from `Updater.Version`, so the file, the Updates screen and the release manifest always agree.

## The build tools in Setup (developer, 2026-11-20)
He also ruled that Python and Zig are not trimmed.
- Setup carries, as resources: the builder kits for the three games (one zip per kit, made by `build-setup.ps1` from kit folders that must match their own `kit-manifest.json` exactly), the official Python embeddable package zip (3.15.2, Windows 64-bit) and the official Zig zip (0.17.1, x86_64 Windows), both unchanged, plus `builder-notices\NOTICES.txt`, `builder-notices\ZIG-THIRD-PARTY-NOTICES.txt` and `builder-notices\PYTHON-THIRD-PARTY-NOTICES.txt` (developer, 2026-11-20: add the notices Python's LICENSE.txt lacks, each text unchanged from its official source).
- They are unpacked into the folder `builder` beside the launcher: `builder\kit`, `kit2`, `kit3`, `python`, `zig` (the Zig zip's top folder is left out), `NOTICES.txt`, `zig\THIRD-PARTY-NOTICES.txt` and `python\THIRD-PARTY-NOTICES.txt`. This is the layout "Build my game..." already looks for (`BuildCore.Find`). A `builder` folder beside the launcher wins over `builder-tools.txt`, so on a developer's PC an installed copy uses the bundled kits, not the ones `builder-tools.txt` names.
- `build-setup.ps1 -Tools <folder>` builds it. The folder holds `kit\`, `kit2\`, `kit3\`, `python.zip` and `zig.zip`; it is not in this repository. `release.ps1 -Tools <folder>` passes it on. A kit with a file its manifest does not list (hidden files included), a missing or changed file, or the wrong game is refused; each kit zip is made from its manifest's list only. The Python and Zig zips are pinned by SHA-256 (Python 3.15.2 embeddable amd64, Zig 0.17.1 x86_64 Windows), because the notices name those versions.
- Install: the whole tools folder is first written into `builder.setup-tmp`, with a progress bar ("Installing the build tools: X MB of Y MB"); its file list, `builder\installed-files.txt`, is written before any file. Then it is swapped in by renaming, with the old folder set aside until everything has worked. If anything fails (a damaged Setup file, a full disk, a game build running from the old tools), the old launcher and the old tools are put back and the staging folder is removed. Setup checks first that the drive has the tools' size plus 200 MB free. Names that would land outside the folder are refused before anything is written. The window cannot be closed while it works.
- Old tools are removed by their own list only; empty folders go too. A file nobody listed (something a user put there) is never deleted: its folder is renamed `builder.kept-<date and time>` and kept; such a folder never blocks a later install. A list line that cannot be a path inside the folder is skipped.
- The uninstaller is a separate small build of the same source without the tools (about 0.4 MB), so the copy in the install folder and the copy each uninstall leaves in the temp folder stay small.
- Sizes on 2026-11-20: Setup file 130.6 MB; installed 20,000 files, 405 MB (tools 19,992 files, 389 MB).

## What Setup does
- One file, `FlutterDeckSetup-<version>.exe`, holding the launcher, the three bundled loops, LICENSE, NOTICE and the build tools (above).
- Installs for the current Windows user only, with no administrator prompt, into `%LOCALAPPDATA%\Programs\Flutter Deck`. The folder is fixed; there is no silent mode and no option that redirects it. This folder is separate from the settings folder `%LOCALAPPDATA%\FlutterDeck`.
- A shortcut named Flutter Deck that already exists and points somewhere else is left as it is, and Setup says so.
- Adds a Start Menu shortcut, an optional desktop shortcut, and an entry in Windows' installed-apps list (current user only) with name, version, publisher, icon and an uninstall command.
- Installing over an existing copy replaces it and keeps settings. It warns when the installed copy is newer. It will not install while the launcher is running and asks the user to close it; it never closes it itself. "Running" includes a launcher that has self-updated or rolled back and not yet restarted, whose file then carries one of the updater's leftover names.
- Files are first written beside their destinations and then swapped in by renaming; each old file is set aside and deleted only after every swap has worked. If a copy or a swap fails, the files already swapped are put back, so the previous install stays as it was, and a failed first-time install leaves no files or empty folders (best effort: a second failure while putting back could still leave a mix). A folder holding only Setup's or the updater's own leftover files can be installed into again, so a failed attempt can simply be retried. Stale updater leftovers (`.old`, `.new`, `.rolledback`, `.old.keep`) are removed so Roll back cannot offer an unrelated build.
- It refuses a folder that already holds other files and no Flutter Deck, anything that is not a full local drive path, and a folder that is a link (junction) to another location.
- The self-updater keeps working in the installed folder because the user owns it. After a self-update the launcher corrects the version shown in the installed-apps list at its next start (`InstallRecord.RefreshVersion`), only when the entry's folder is the folder it is running from.

## What Uninstall does
- `Uninstall Flutter Deck.exe` in the install folder (also reached from Windows Settings > Apps) is the same program. It copies itself to the temp folder and reruns from there so the install folder can be removed. That copy (the whole Setup file, about 8 MB) is left in the temp folder each time, including when the user cancels; Windows' own temp cleanup removes it.
- It acts only on a folder that holds the uninstaller Setup put there. A folder that merely contains a `FlutterDeck.exe`, such as a portable copy or a source checkout, is refused, whatever path it is given.
- Removes the build tools by their list first (also a staging or set-aside copy a failed Setup left), then only a fixed list of file names: the installed files, Setup's own temporary files, the updater's leftovers and, last, the uninstaller. A tool file in use (a game build running) makes the removal partial, so the uninstaller stays for a retry. If any file cannot be removed, the uninstaller, shortcuts, installed-apps entry and settings are left in place, the window says the removal was only partial, and Uninstall can be run again. It never deletes a folder's contents wholesale. The install folder is removed only if it ends up empty; anything else the user put there is kept and reported.
- Removes the Start Menu and desktop shortcuts only if they point at this install, and the installed-apps entry only if it names this folder.
- Settings are kept unless the user ticks the box, which is off by default. When ticked, only the launcher's own settings files are removed by name (each file, its backup and its temporary copies), and the window says so only if none of them remain. Game, BIOS, save and music files are never touched; the settings only point at them.
- It will not uninstall while the launcher is running.

## Structure and commands
- `InstallCore.cs`: file operations, no UI, registry or shortcuts; every folder is a parameter. `InstallPureTest.cs` tests it on a scratch folder.
- `Setup.cs`: the window, shortcuts and the installed-apps entry.
- `build-setup.ps1`: builds `.dream-loop\setup\FlutterDeckSetup.exe` around the `FlutterDeck.exe` in the folder (or the file given with `-LauncherPath`).
- `release.ps1` builds the installer around the exact launcher file it signed and places it in the release folder with the launcher file and the release zip.
- `build-zip.ps1 -SetupPath <installer> -LauncherPath <launcher> -OutZip <zip>` makes the release zip (developer, 2026-11-21). It runs the installer's own Install code from that installer into a temporary folder, removes the uninstaller and `builder\installed-files.txt`, checks the launcher inside is the given file, and zips the folder as `FlutterDeck\` with `/` in entry names. So the zip holds exactly what Setup installs, the build tools included. Before zipping it refuses a folder that is not exactly Setup's file list (`Installer.Payload` and the builder files). The uninstaller never acts on an unzipped copy (it has no uninstaller). Setup does accept a folder that holds `FlutterDeck.exe`, so a copy unzipped into Setup's own folder (`%LOCALAPPDATA%\Programs\Flutter Deck`) and then installed over keeps its old builder folder aside as `builder.kept-<time>` (about 400 MB) that nothing removes; the zip's folder is named `FlutterDeck`, not `Flutter Deck`, so this needs a deliberate rename. `check-installer.ps1` builds a zip from the stand-in installer and checks its contents and the refusal of a wrong launcher file.
- Check: `powershell -NoProfile -File .\check-installer.ps1`

## Limits
- Neither the launcher nor Setup has a Windows publisher (Authenticode) signature.
- Per-user install only; no all-users install. No install-folder choice. No repair mode.
- If Setup is run on a PC where an older build already added its entry from a different folder, the entry is overwritten to point at the new folder.

## Verification
- 2026-11-20, build tools: `InstallPureTest.cs` covers install with tools, replace, a held tool file during replace (everything put back), a damaged tool zip, unsafe names (`..`, rooted, drive and device forms), a full drive, a crashed staging folder, partial and full uninstall, a list naming a file outside the folder (not followed) and unlisted files kept aside. `check-installer.ps1` builds Setup with small stand-in tools and checks every resource is in it, the uninstaller is the small build, and a kit with an unlisted file is refused.
- 2026-11-20, real payload: the installer's own Install code, run from the built Setup file with its real payload into a scratch folder whose path has a space, took 13.6 s and 15.9 s in two runs on the developer's PC (20,000 files); Uninstall took 44.6 s and removed everything. From that folder Python 3.15.2 ran, Zig compiled and linked a small C program that ran (98 s the first time, while Zig built its Windows C library), and `BuildCore.Find` accepted the tools for all three games. NOT verified: running Setup itself (its window, progress bar, registry entry and shortcuts) with the tools, a full game build from the installed tools, and the time on another PC.
- The independent check on 2026-11-16 found three faults (a part-replaced install after a mid-way failure, a self-updated launcher not seen as running, and uninstall accepting any folder with a launcher in it) and smaller ones; they were fixed and are covered by the tests below. It also confirmed, with scratch files only, the uninstaller's hand-off to its temp copy and that shortcut removal keeps a shortcut pointing elsewhere.
- Verified by tests on scratch folders: fresh install, replace (including a read-only launcher), failed copy and failed swap both leaving the old install intact, refusal while the launcher file or an updater leftover is held open, refusal of a folder holding other files, of a folder with a launcher but no uninstaller, of drive roots and of relative, drive-relative, network and device paths, uninstall removing only known files and keeping the user's own file, by-name settings removal, version comparison.
- Verified with a real running program in a scratch folder: it is detected as running and uninstall is refused.
- Verified on built files in a scratch copy: both `FlutterDeck.exe` and the Setup file carry the product name, company and version 0.3.0, an `asInvoker` manifest (no administrator prompt), and the icon; a running scratch launcher's window reports the icon; the Setup window opens and shows the expected text. Setup was closed without pressing Install, and no install folder, registry entry or shortcut existed before or after.
- NOT verified: replacing an existing install for real, the "newer version installed" warning, a failed install on a real PC, ticking the settings-removal box for real, the version refresh after a self-update, how the icon and the entry look by eye in Explorer, the Start Menu, the taskbar and Windows Settings, a desktop that is not OneDrive-synced, and behaviour on any other PC or Windows version.

## Real run on the developer's PC, 2026-11-16
Driven through UI Automation (no mouse or keyboard), with the Setup built from the working-copy launcher (SHA-256 `0D055F4B9136FDB692602EB2660B20EB61FB262085B69E517E4BDA6D4039D3B0`). Starting state: no install folder, no installed-apps entry, no shortcuts.
- Install: Setup reported "Flutter Deck is installed" and exited with code 0. The folder held exactly `FlutterDeck.exe`, `LICENSE`, `NOTICE.md`, `Uninstall Flutter Deck.exe` and `assets\FlutterDeck-OriginalLoop.wav`; the installed launcher was byte-identical to the working-copy one. The installed-apps entry (current user only; no machine-wide entry) had name Flutter Deck, version 0.3.0, publisher Dead Signal Interactive, the icon, the folder and the uninstall command. Start Menu and desktop shortcuts pointed at the installed launcher. The launcher started from the install folder and reached Home.
- While that launcher ran: Setup over the existing install said "Flutter Deck 0.3.0 is installed and will be replaced" and, on Replace, refused with "Flutter Deck is running... Setup does not close it for you". The test script could not dismiss that message box, so that Setup process was ended by its process id; the launcher file was not separately re-checked at that point, but it was still present and the launcher still running when Uninstall was tried next. Uninstall handed over to its temp copy, showed the settings box off, and refused with "Flutter Deck is running"; the launcher file, LICENSE, the installed-apps entry and the Start Menu shortcut were then confirmed present (the other files and the desktop shortcut were not re-checked at that point).
- Uninstall (settings box left off): reported "Flutter Deck was removed" and "settings were kept". Afterwards the folder, the installed-apps entry and both shortcuts were gone, the parent Programs folder remained, and the developer's settings folder was byte-identical to before the test.
- Each uninstaller start left one temp copy of Setup in the temp folder (two in this run), so uninstall did not remove everything it created; an AI assistant deleted those two by hand afterwards.
- Evidence trail: the driving script was edited between steps (the Setup-refusal step was removed from it after it ran) and the settings baseline file was rewritten after the run, so those two results rest on the session's console output, not on files that can be re-read. An independent read-only check afterwards found no install traces and no settings file modified during the test.
- The developer's desktop is OneDrive-synced, so the desktop shortcut existed there briefly, between the install and the uninstall.
