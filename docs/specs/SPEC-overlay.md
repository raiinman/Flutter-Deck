# In-game overlay

Status, 2026-11-16: built on the branch `overlay` (the first phase is committed as 18479f4; the key editor below is the second phase) and tested against a stand-in game window. It has NOT been used over the real game: no real mouse hover, no real hotkey press, no real key press in the editor and no real focus change has been tried. The picture presets and every control that needs the game to listen are not built (see "Not built").

## Developer decisions (2026-11-16)
- The overlay opens two ways: a small bar when the mouse reaches the top of the game window, and a hotkey. Layout idea from the developer's screenshot of another program: a small pill centred at the top with pause, restart, stop, full screen and a menu; nothing of that program is copied.
- Answers to the open questions, given in the overlay project: the hotkey is **Ctrl+Alt+O and changeable**; the bar shows **in a window and in full screen** (a setting limits it to full screen); opening the overlay **does not pause** the game.
- Picture presets are chosen in the overlay and applied by DSI Prism. Nothing is built for them here.

## What the user gets
- Move the mouse anywhere in the top 90 pixels of the game picture: the pill appears at once at the top centre. Move away and it goes after about 1.2 seconds.
- Press Ctrl+Alt+O while the game is in front: the bar opens and stays (pinned) until the hotkey is pressed again or the player switches to another program.
- The pill has the kit's five buttons, in this order: **Pause**, **Restart session**, **Stop session** (asks the game to close, after a second click within three seconds) and **Fullscreen**, which are for the game, and **Deck menu**. Pause and Fullscreen are drawn disabled until the game can act on them; Restart is the launcher's own and works (below). Music is not on the pill.
- The Deck menu opens the kit's six menus (see the section above). A line beside the menu shows the result of a key change, or why the hotkey does not work. The key editor opens from Help > Controls reference.
- The overlay takes the keyboard from the game only in two cases: while the player is choosing a key, and (since 2026-11-19) when the overlay key opened the overlay and Keyboard control is on (see Keyboard control below). The hover bar never takes it. Clicking the bar does not make it the foreground window.

## What the bar shows, and why not more
The pill's controls come from `OverlayLayout.Pill`. Stop, restart and menu are the launcher's own and always work. Pause, full screen, volume and screenshot need the game to listen while it runs, which the game side has not built (REQUEST-game-live-control.md). They are shown today, disabled. Their feature names must come from the game's own `--identity` answer (`features=a,b,c`); the table in `OverlayLayout` holds `null` for each, so even a build that happened to list a feature called "pause" does not make the button appear. When the game side names them in its contract, fill the name in that table and add the button in `GameOverlay.cs`. Never guess a name. The launcher passes `OverlayFeatures.None` today.
- Restart: the developer decided on 2026-11-17 that the launcher does it (close, then start again); see the launcher-side controls below.
- Full screen from the bar is blocked: the game keeps F11 and Alt+Enter, and the launcher never sends keys to the game.

## The key editor (Game keys...)
- Opens from the menu. It shows the game's fourteen buttons in two columns, each with its current key. Click a button, then press the key you want; Esc cancels the wait; a second Esc, or Back, closes the editor. Save keys, Discard changes and Default keys are footer buttons. Save and Discard are off until something changed, and Save is also off while a button has no key.
- **The overlay holds no draft and writes no key file.** (One exception, a diagnostic trace, changed 2026-11-19: the overlay writes its state changes, errors and the process number and window class (never the title) of the window that has the front to `fd-overlay-trace.txt` in the temp folder, or to the file named by the environment variable `FLUTTERDECK_OVERLAY_TRACE`. It was opt-in before; it is on now, because a real-game fault (overlay missing after Return to launcher) could not be diagnosed after the fact. The file is replaced at each launch and stops at 300 000 bytes; it holds no file contents. `run-with-overlay-trace.cmd` still works. Not tested.) It edits the launcher's own draft (`keyDraft` in `Program.cs`) through `OverlayHost` callbacks (`KeyDraft`, `EditKey`, `KeysDirty`, `SaveKeys`, `DiscardKeys`, `DefaultKeys`, `KeyWarning`). The swap rule, the refusal of Tab, F11 and F12, the written file shape and the `.bak` all stay in `KeyMap.cs`. The map is still written from exactly one place: the launcher's `SaveKeyDraft`, which the Save button on the setup screen and the overlay both call. Unsaved edits are therefore shared with the setup screen. `check-overlay.ps1` fails if `GameOverlay.cs` touches files, loads or copies the map, calls `SetSingle`, or saves anything except the overlay's own settings; this is a text search of that one file, not a proof, and `check-keys.ps1` separately requires exactly one `keyDraft.Save(` in `Program.cs`. Leaving the editor with unsaved edits says so in the menu note.
- It uses the same keyboard mode as choosing the overlay key: the overlay takes the keyboard (the game does not act on keys then) until the editor closes, the overlay loses the keyboard, or it cannot take it within 1.5 seconds. Keys do nothing until a button is clicked. The overlay hotkey is released while the editor is open and registered again afterwards, and it is checked again then against the game's key map as saved on disk (the unsaved draft is not used), so a key you have just mapped and saved cannot stay the overlay key. Not covered by a test.
- A pressed modifier (Ctrl, Alt, Shift) is taken as the key at once, as on the setup screen; AltGr arrives as Left Ctrl (SPEC-keys.md).
- Saved keys apply the next time Play is pressed; the game reads its key map only at start (SPEC-keys.md).

## The pill and its menus (the developer's kit, 2026-11-17)
- Layout numbers come from `Flutter-Deck-Top-Pill-Menu-Kit.zip`: a 300 by 64 pill 27 px below the top of the game picture, five 48 by 44 buttons 4 px apart (Pause, Restart, Stop, Fullscreen, Menu), a 174 wide menu below and to the right (Library, Session, View, Saves, Audio, Help), and a 286 wide submenu beside it. Colours, the red seam, the gold studs and the hover, pressed and disabled looks are the kit's. Everything is drawn in code from path data; no picture files.
- **Pause, Restart, Stop and Fullscreen are controls for the game, never for music.** Stop and Restart work now (two clicks each; the launcher does both). Pause and Fullscreen are drawn disabled until the game can act on them (`OverlayLayout.GameControls` and REQUEST-game-live-control.md). Music is only the Audio menu's rows.
- **Second-click confirmation (Stop, Restart):** the first click turns the button's plate red and shows a small caption under the pill ("Stop session? Click again."); a second click within three seconds does it. The older red "End?" block inside the button was replaced on 2026-11-17 at the developer's request.
- **Quick bar only in full screen is greyed out** (developer, 2026-11-17: not working right now). The row is disabled and a `full-screen-only = yes` line in `overlay.txt` is ignored (`FullScreenOnlyWorks` in `GameOverlay.cs`); the pure `OverlayState.FullScreenOnly` rule is still tested.
- Menu rows follow the kit's `labels.json` (21 rows). A row works only when the overlay has an action for it; all others are disabled, as the kit says unsupported actions must be. Working rows today: Session > Stop session and Restart session, Library > Return to launcher, Audio > Music playback, Mute music and Music volume, View > UI scale, Help > Controls reference (opens the key editor), Setup guide and About Flutter Deck. Rows added by us, not in the kit: View > Quick bar (hover) and Quick bar only in full screen, Audio > Next music track, Help > Overlay key (all working); and, disabled until the game or DSI Prism offers them (the developer asked for these to be listed greyed out): Session > Reload key map and Game status, View > Take screenshot (F12) and Picture preset, Audio > Game volume and Mute game audio.
- **Launcher-side controls, wired 2026-11-17** (each is a callback in `OverlayHost`; the launcher does the work, the overlay only asks): Restart (pill button and Session > Restart session: two clicks, then the launcher asks the game to close and starts it again once it has ended, only within 30 seconds, and the request is used up by the first end of the game, a Stop, or a manual Play), Library > Return to launcher, Help > Setup guide and About (bring the launcher to the front on its Home, Setup and Help screens; they do not change screens while the player is on Setup, so a half-done setup is never reset), Audio > Mute music and Music volume (a bar you click or drag; the launcher's own slider follows), View > UI scale (minus and plus on the launcher's text size, 80 to 120 percent). Game volume is not offered: the developer plans audio enhancement later and wants that designed first.
- **Quick bar switch (developer, 2026-11-17).** View > Quick bar (hover) turns the hover pill off for good (saved as `quick-bar = no` in `overlay.txt`); the hotkey still opens the pill. `overlay = no` in `overlay.txt` starts no overlay at all (no pill, no hotkey); there is no menu row for that because the menu is part of the overlay. The quick bar cannot be turned off while the overlay key is not registered, since nothing else could open the overlay then. 
- A bar closed on purpose (hotkey, Stop) stays closed until the cursor has left the band and returned; without this, no-dwell hover would reopen it at once.

## When the bar wakes, and when it goes
All timing is in `OverlayState` (milliseconds passed in, so tests do not wait).
- Waking needs the game window in front, a known cursor, and the cursor inside the hot zone. There is no delay: the bar shows on the first 40 ms tick. The hot zone is the top 90 device-independent pixels of the game picture, across its whole width (numbers read from another emulator's pill: REFERENCE-pill-behaviour.md, changed 2026-11-17 at the developer's request). The pill sits 27 pixels below the top edge, centred. With "only in full screen" on, a game picture that is not exactly a monitor (within two pixels) does not wake the bar.
- It leaves 1,200 ms after the cursor was last in the hot zone or on the bar. An open menu does not time out: it ends with a click on the menu button, the hotkey, or the game losing the front.
- A bar opened by the hotkey ignores the cursor. Any bar closes at once when the game is no longer in front, when the game window is gone, hidden or minimised, and when the launcher closes.
- The hotkey does nothing while another program is in front, except to close an overlay that is already open.

## The hotkey
- A global key combination registered with Windows (`RegisterHotKey`, no keyboard hook, no input injection). It is registered only while a game is attached and released when the game ends or the launcher closes. Windows keeps the combination from every program, so no game key receives it. The modifier keys themselves still reach the game: that is why a combination whose modifier is one of the game's own keys is refused.
- Rules (`HotkeyRules.Check`): the key is a letter, digit, F1 to F10, Space, Insert, Delete, Home, End, Page Up or Page Down. Never Tab, F11, F12 or Enter (the game keeps them; Alt+Enter too). A letter, digit or Space needs Ctrl or Alt (Shift alone would break typing everywhere). A bare key is allowed only as F1 to F10, and not if the game's key map uses it. Alt+F4 and Ctrl+Alt+Delete are refused. A modifier is refused if the game's key map uses that modifier (the map is read when the key is chosen).
- If Windows refuses the combination (another program holds it), the menu says so and the old choice stays; at start-up the same text shows under the menu.
- Choosing a key takes the keyboard on purpose: the overlay stops being a no-activate window, asks Windows to bring it to the front, and reads the next key. The game does not act on keys then (game side's statement: it acts on keys only while its own window is in front). If the overlay has not become the active window after 1.5 seconds it gives up with a note and the game keeps the keyboard. Esc, losing the keyboard, or a good key ends the mode, and the foreground goes back to the game window.

## Finding the game window
By the game's own process id first. Of that process's visible windows, the one whose class is `RuntimeGpuPresent` or whose title starts with `rock_neo_rt live` is used. These are the game side's facts of 2026-11-16, not contract promises. The picture rectangle is the client area in screen pixels, read every 40 ms, so the bar follows a moved or resized window.

## Window behaviour
- A transparent, topmost tool window with no taskbar button and `WS_EX_NOACTIVATE`; clicks answer `MA_NOACTIVATE`. It sizes itself to the bar (and the menu below it) and is only moved, never resized, by the launcher. Everything is drawn inside that one window; the overlay opens no pop-up windows of its own (button tooltips are WPF pop-ups; not observed).
- Placement is by `SetWindowPos` in physical pixels, from the window's own scale. It sits 10 device-independent pixels below the top edge and is kept inside the game picture.
- It is drawn only over a borderless game window. The game side says full screen is borderless, never exclusive. Exclusive full screen would hide the overlay.
- Any failure in the overlay (five errors in a row) removes the overlay; it never stops the game or the launcher.

## Settings
`overlay.txt` in the launcher's settings folder: `hotkey = Ctrl+Alt+O`, `full-screen-only = no` (greyed out, ignored for now), `quick-bar = yes`, `overlay = yes` (no starts no overlay at all), `keyboard-menu = yes` (keyboard control after the overlay key) and `pause-on-open = no` (kept for later; nothing reads it yet). Written through a temporary file with the previous file kept as `.bak`, CRLF, no byte-order mark. A missing, oversized or damaged file gives the defaults; a hotkey in the file that breaks the rules is replaced by the default. The key editor's `keys.ini` is not touched by this unit. The saved hotkey is checked against the game's key map every time it is registered, not only when it is chosen.

## Structure and command
- `OverlayCore.cs`: geometry, state machine, hotkey rules, settings, feature gating. No window code.
- `GameOverlay.cs`: Win32 helpers, the game window probe (`IGameProbe`, so tests can supply the cursor), the overlay window, the hotkey, the key-choosing mode.
- `OverlayPureTest.cs` and `OverlayHostTest.cs`; command: `powershell -NoProfile -ExecutionPolicy Bypass -File .\check-overlay.ps1`
- Changes outside these files (for the launcher project, all marked `overlay:` or one line each): `build.ps1` lists the two files; `Program.cs` has a field `overlay`, `StartOverlay` and `StopOverlay` (about 15 lines, placed before `GameEnded`), one call in `PlayGame` after a game starts, one call in `GameEnded`, and `StopOverlay();` at the start of the window's `Closing` handler. The music buttons call the launcher's `audio` through callbacks; the Stop button calls `GameRuntime.RequestClose`.

## Game settings, 2026-11-18

Session > Game settings... opens a panel beside the Session menu. It shows the play settings the game program offers, so the player can change one while playing and then press Restart to apply it. The panel is kept short so it fits under a 480p game picture: "Restart to apply changes..." is the first row, then one compact (30 px) row per setting, then a status line. There is no Back row; pointing at another menu name leaves the panel. The window test asserts the whole overlay is at most 453 px high with nine settings open (it fits a 480 px picture with the pill's 27 px margin).

- **Where the values live.** The overlay keeps no copy and writes no file. `OverlayHost.GameSettings` gives the rows (`GameSetting` in OverlayCore.cs), `SetGameSetting` asks the launcher to change one, and `GameSettingsPending` says whether the next start would differ from the running game. The launcher side is `OverlayGameSettings.cs`: it builds the rows from the saved settings and the program's reported features, applies one click to the settings object, and compares the arguments the game started with against the arguments it would get now, using the same function that starts the game (`GameRuntime.BuildArguments`). A setting the program ignores, or one that another setting overrides, therefore never lights up "Restart to apply".
- **Which game.** The launcher takes the settings object and the feature check of the game that was started (not of the game shown on screen) when the overlay attaches, and saves with that game's number. Restart then starts that same game with them.
- **Rows.** Window size (480p to 4K, or 2x to 6x for an older program), Sharper picture, Smooth movement, Controller vibration, Vibration strength (0 to 100 percent), Opening movie, Third-person controls, Camera speed, Invert camera up and down. A switch shows a tick; a choice shows its current entry on the right and a click goes to the next one and wraps round. A row appears only when the game program reports the option.
- **Rules copied from the launcher.** With third-person controls on, smooth movement is fixed on, so its row is greyed out with the reason. Camera speed and invert need third-person controls. Vibration strength needs vibration on. A greyed-out row cannot be clicked.
- **Restart to apply.** It is greyed out until something really differs. It uses the same two-click arming as the pill's Restart (the first click asks, the second restarts, an unanswered ask expires after three seconds), so unsaved play is never lost by one click.
- **Not offered, on purpose.** Game volume and mute (the developer decided that audio enhancement is designed first). Aim style (the launcher removed that box and ignores a saved value). Camera distance (not asked for yet). Target lock-on IS offered since 2026-11-19: the settings file keeps it as `lockOff`, and it needs third-person controls, as the launcher's start arguments say.
- **A refused or unsaved change.** The launcher returns a line, and the status line shows it.
- **Checks.** `OverlayGameSettingsTest.cs` (48 checks: rows per feature set, every change, the dependency rules, the settings file round trip, the session wiring `OverlayGameSettings.ForSession`, and "differs") and the panel flow in `OverlayHostTest.cs` with stand-in callbacks, including a picture of the panel. Rows are 26 px high so ten settings still fit under a 480 pixel picture. The launcher-side file is guarded to stay pure in `check-overlay.ps1`, and `Program.cs` may reach it only through `ForSession`. Not tested: a real game restarting with changed settings.

## Keyboard control, 2026-11-19
Not run over the real game. Built and tested against a stand-in game window, a fake probe and a pretend front window.
- **When.** Only when the overlay key opens the overlay (the player is at the keyboard then). Hover never starts it. Help > "Keyboard control (overlay key)" turns it on or off, and the choice is saved as `keyboard-menu = yes` or `no` in `overlay.txt`. Default: on. Off means the overlay behaves exactly as before.
- **How it starts.** The window stops being a no-activate window and asks Windows to bring it to the front. If it is not in front after 1.5 seconds it goes back to mouse use with no note, and the mouse menu still works.
- **Keys.** Left and Right move along the pill (greyed-out buttons are skipped, the highlight wraps). Down opens the menu. Up and Down move along the six names, and each name shows its rows. Right or Enter goes into the rows. Up and Down move along the rows (greyed-out rows are skipped). Enter or Space does what a click does. A row that opens another panel (Game settings, Picture preset) is entered at once. Left goes back one level. Esc goes back one level too, and on the pill it closes the overlay. A held arrow key repeats. Other keys do nothing. The overlay key itself still closes the overlay, because Windows delivers it before any window sees it.
- **The highlight** is a cyan ring drawn over the chosen button. It is not a keyboard-focus rectangle: the buttons stay not focusable, so the mouse look is unchanged.
- **Closing.** Esc on the pill, the overlay key, a row that closes the overlay (Stop, Restart) or switching Keyboard control off gives the front back to the game window, but only if the overlay still holds the front. After Alt+Tab to another program it does not pull the game back.
- **Separate from the key-choosing mode.** Choosing the overlay key and the key editor keep their own rules, and they end keyboard control first.
- **Left out.** The music-style volume bar and the UI scale row have no keyboard use (they are not buttons).
- **Real-game risks, not tested.** The game loses the front while the player may still hold the overlay key's Ctrl or Alt, so the game could think a key is stuck until the key is pressed and released again. The game must not minimise when it loses the front (exclusive full screen may). Both are the reason Keyboard control can be switched off in Help.

## Screen scale, 2026-11-19
- **What the program is.** The launcher is system screen-scale aware (read with `IsProcessDPIAware` and `GetProcessDpiAwareness` in a scratch program built like the launcher: WPF makes it so). The overlay reads the scale from its own window every tick, also while hidden. Before this change it read it only while shown, so the first hover band used 100 percent.
- **Fit.** An open menu taller than the game picture (a small window at a high scale) shrinks the whole overlay, in steps of 0.05 and never below 0.6. It only shrinks while the overlay stays open, so it does not jump, and it goes back to full size when the overlay closes. At 100 percent a 480 pixel picture is not shrunk by the Game settings panel (452 dip plus the 27 dip margin). The View menu, with ten rows, is taller than 480 dip and does shrink there.
- **Second monitor with another scale (done 2026-11-19, not seen on a second monitor).** `FlutterDeck.manifest` (embedded by `build.ps1`) declares PerMonitorV2, and `AppInfo.cs` declares target .NET Framework 4.8, which WPF needs to rescale a window when it changes monitor. Checked with a scratch program built the same way (it reported per-monitor awareness 2) and by finding both in the built exe. With one monitor, or monitors at the same scale, nothing changes. Not tried on two monitors with different scales: the launcher's own pixel code (resize ghost, scaling profile) was not looked at under a scale change.
- **Tested.** With a pretend scale (the real window keeps this machine's scale): the hover band depth, the pill size and place at 150 percent, shrinking at 200 percent on a 720 pixel picture, and the return to full size. Not tested: a real 125, 150 or 200 percent screen.

## Back to the game from the launcher, 2026-11-19
- **Why.** Library > Return to launcher, Help > Setup guide and Help > About bring the launcher to the front. The overlay then hides on purpose (it follows the game, and the game is no longer in front), and the game sits behind the launcher.
- **What.** While the launcher window is in front and a game is running, the overlay key brings the game window to the front and opens the overlay. It does this only when the launcher itself is in front. With another program in front the key still does nothing, so it cannot pull a game forward while the player works elsewhere.
- **Detail.** The overlay counts the game as in front for 1.5 seconds after the key, because Windows may take a moment. With Keyboard control on, the overlay then takes the keyboard as it does after any overlay-key open.
- **Not run over the real game.** Tested with a stand-in game window and a pretend launcher-in-front answer. A clickable way back (a button in the launcher) is not built.

## Live control of the game: built 2026-11-23 (contract 2.34), not played
- **What works in the code.** For a game program that lists `live-control` in `--identity` (Legends 1 only), the launcher passes `--control-file <data folder>\live-control.txt` and the overlay offers: Pause and Resume (pill button, Session > Resume game), Fullscreen (pill button, View > Fullscreen), Take screenshot, Mute and a game volume bar. A program without the word gets the same controls disabled, as before. The overlay never sends keys or messages to the game: it hands one command line to the launcher (`OverlayHost.GameCommand`), and `LiveControl.Send` in `GameRuntime.cs` writes the file.
- **Writing rules (game contract, `LAUNCHER-CONTRACT.md` section 41).** The game renames the command file to `.taken`, reads it and deletes it, and reads at most 32 lines and under 1024 bytes per file. So the launcher never rewrites a file the game might be taking (that would run commands twice, which a checker proved on the first version). Commands wait in memory in `LiveControl`; the next file is written, as a temp file and then a rename, only when the last file is gone; a timer retries every 40 ms. A file holds at most 30 lines and 900 bytes. A newer `volume`, `pause`, `mute` or `speed` line replaces an older one that still waits. When 200 commands wait, the next ones are refused and logged (`live-control-failed`), not dropped quietly. A new game clears everything that waited for the old one before it deletes the old files. Commands: `pause on|off`, `fullscreen toggle`, `screenshot`, `volume 0-100`, `mute on|off`, `speed unlimited|normal`. The launcher does not pass `--mute` or `--audio-silent` unless the player chose mute.
- **The game's state file.** The game rewrites `<control path>.state` (paused, volume, mute, fullscreen, last_screenshot, unlimited_speed). The launcher reads it with sharing allowed (`LiveControl.ReadState`) and the overlay follows it about twice a second while it is shown, so Esc in the game (which ends a pause), a player's own F11 or a volume change show correctly. For 1.5 seconds after the overlay's own command the old state is ignored, so a click or a volume drag is not undone. A new screenshot is named in the menu note ("Screenshot saved: shot_fNNNNNN.bmp"). The screenshot is the 320 by 240 picture, not the sharp one.
- **Unlimited speed.** View > Unlimited speed (the game's Tab key) sends `speed unlimited` or `speed normal` and is ticked from the state file.
- **Keyboard.** The game volume bar, like the music bar, is mouse only. Pause, Fullscreen, Screenshot and Mute are buttons and work from the keyboard.
- **Checks.** `OverlayHostTest.cs` section "live control of the game" (stand-in launcher callbacks, a stand-in game window) and `GameRuntimePureTest.cs` (arguments, identity, command file writing and the state file). Not tested: the real game. The game's own test program `rock_neo_rt_lc.exe` has not been run with the launcher.
- **Not built.** A button in the launcher to return to the game; the sharp-picture screenshot; a way to see where screenshots go (only the file name is shown).
